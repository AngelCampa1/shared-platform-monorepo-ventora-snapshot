# Engineering log

The strictness settings, the release flow, and the tooling that keeps this repository's own
documentation honest. Test tiers, coverage, and the quality gate are covered separately in
[TESTING.md](TESTING.md); this document picks up where that one stops.

Every number below is read from `docs/metrics.json`, which is generated by
`scripts/repo-metrics.mjs` from the working tree. Nothing here is typed in by hand except the prose
around it.

## Strictness settings, quoted from the configs

Not a summary: the actual flags.

`tsconfig.base.json`, inherited by every package:

```json
"target": "ES2022",
"module": "NodeNext",
"moduleResolution": "NodeNext",
"strict": true,
"exactOptionalPropertyTypes": true,
"noUncheckedIndexedAccess": true,
"noImplicitOverride": true,
"forceConsistentCasingInFileNames": true,
"isolatedModules": true,
"verbatimModuleSyntax": true
```

`exactOptionalPropertyTypes` and `noUncheckedIndexedAccess` are the two that actually cost
something to live with. The first stops `{ x?: string }` from silently accepting `undefined` as an
assigned value; the second makes every array index and record lookup return `T | undefined` until
you narrow it. Both generate real friction in day-to-day work. `skipLibCheck: true` is on, so
third-party declaration files are not type-checked, a deliberate speed trade stated rather than
hidden.

`biome.json` linter rules, on top of `recommended`:

```json
"suspicious": { "noExplicitAny": "error", "noConsoleLog": "warn" },
"correctness": { "noUnusedVariables": "error", "noUnusedImports": "error" },
"style": { "useConst": "error", "noVar": "error" }
```

`noExplicitAny` is an error, not a warning, so `pnpm lint:ci` fails on a single `any`. Formatting is
fixed at 100 columns, two-space indent, double quotes, trailing commas, semicolons.

`py/pyproject.toml`:

```toml
[tool.ruff.lint]
select = ["E", "F", "I", "N", "UP", "ANN", "S", "B", "A", "C4", "T20"]
ignore = ["ANN101", "ANN102"]

[tool.mypy]
python_version = "3.12"
strict = true
ignore_missing_imports = false
```

`ANN` requires annotations on every function. `S` is the bandit security rule set. `T20` bans
leftover `print` calls. `ignore_missing_imports = false` means an untyped dependency is an error
unless it is listed in an explicit override: there are two, one for `boto3`/`botocore` and one for
`fastapi`/`sentry_sdk`, both visible in the file.

## The document's own numbers are gated

`scripts/repo-metrics.mjs` follows the same contract as `scripts/codegen-schemas.mjs`: source of
truth → generated output → byte-compare → exit 1. It walks the tracked file list, counts lines
and test cases, parses every `vitest.config.ts` and `pyproject.toml` for coverage settings, writes
`docs/metrics.json`, and injects the result into marker-delimited blocks in `README.md` and
`portfolio/TESTING.md`. `pnpm run metrics:check` regenerates all of it in memory and fails if
anything on disk differs.

The consequence is small but real: a stale number in this document is a build failure, not a
reader's problem.

Since the counting rules decide what those numbers mean, they get tested to the same standard as
the code they measure. `scripts/__tests__/repo-metrics.test.mjs` holds 18 cases, and the
interesting ones are the adversarial ones:

- `it.each([1, 2, 3])("case %i", ...)` counts as one case, not three.
- The tagged-template form ``it.each`...` `` also counts as one.
- Modifier chains (`test.skip`, `it.only`, `it.concurrent`) still count.
- `describe` blocks do not count.
- A commented-out `it("...")` does not count.
- A string that merely contains the text `test(` does not count.
- Property access such as `obj.test(` does not count.

The last three are the ones that quietly inflate every hand-rolled test counter. They are covered
because the alternative is a number that nobody, including its author, has a reason to believe.

## Release and consumer verification

Packages here are published, not deployed. Product repositories consume them by version.

```text
pnpm changeset            # author a changeset for any package-touching change
pnpm release:cloudflare   # verify → build → scripts/publish-cloudflare-registry.mjs
pnpm release:python       # verify → check-affected:all → scripts/publish-python-registry.mjs
```

Both release paths run the full `pnpm verify` chain first, so nothing reaches a registry without
clearing the same nine steps described in [TESTING.md](TESTING.md#pnpm-verify-the-nine-steps). The
Python path additionally runs `node scripts/run-affected-checks.mjs --all`, which exercises ruff,
mypy, and pytest for every Python package rather than just the staged ones.

The consumer harnesses are the last check before publish, and they are the only ones that test the
package boundary as a consumer sees it:

- `test-consumer/ts-consumer` depends on 14 `@ventora/*` packages and imports them through their
  `exports` maps, including subpath exports like `@ventora/analytics/browser` and
  `@ventora/analytics/server`.
- `test-consumer/py-consumer` installs with `--no-editable --reinstall`, so it imports built
  artifacts rather than the workspace source tree.

Five packages are Cloudflare Workers that deploy rather than publish: `@ventora/email-renderer`,
`@ventora/ai-sdr-worker`, `@ventora/ai-cs-worker`, `@ventora/package-registry`, and
`@ventora/python-registry`. Fifteen packages publish. Eighteen of the twenty carry no runtime
dependencies at all.

This repository does not use a hosted CI service, by policy. No GitHub Actions, no status checks,
no build matrix. What is bought in exchange is narrower than it sounds: the identical gate runs on
the machine that writes the code, so there is no gap between the local environment and a CI image,
and there are no CI minutes to ration when the coverage suite is slow. That is a reasonable trade
for a single-maintainer repository. It would be a bad trade for a team, and it is not presented as
a best practice. The costs are named in full in
[TESTING.md's "Limits" material](TESTING.md#pnpm-verify-the-nine-steps): no fork protection, no
build matrix, no enforcement against `--no-verify`, no shared build history a third party can
inspect.

## Documentation assets

The images in this document and its siblings are generated, and the rules for generating them are
part of the gate's credibility.

- Terminal SVGs come from `scripts/docs/capture-terminal-svgs.mjs`, which runs the real command and
  renders its real output through `scripts/docs/term-svg.mjs`. Charts come from
  `scripts/repo-metrics.mjs --charts`. Product screenshots come from
  `scripts/docs/capture-docs-shots.mjs`; email previews from
  `scripts/docs/render-email-previews.mjs`.
- No asset exceeds 250KB. Documentation that takes a visible moment to load stops being read.
- No asset is ever sourced from `output/`. That directory is gitignored and holds live production
  captures, including real session content, and ad hoc mid-animation frames: `output/shots/` and
  `output/playwright/` in the source repository hold screenshots taken before the widget's
  fade-in transition finishes, which is why several show near-invisible reply text. A second, real
  defect turned up in the same directories on review: several "answered" captures across the six
  products this widget shipped to render the assistant's reply as literal `**asterisks**` instead
  of bold text, a markdown-rendering bug in the hosted client that was never fixed before the
  products it shipped to retired. Assets in `portfolio/screenshots/` are regenerated against the
  local mocked harness, with animations disabled before the shutter fires, never copied out of a
  production run or an ungated capture.

All generated images live under `portfolio/screenshots/`, alongside this repository's other
portfolio documents, so a referenced image and the document that references it move together.
